The route to an administrative session on Thornbury's database server is an identity and authorization problem, not a local exploitation challenge. I must navigate the domain's trust architecture to systematically acquire an identity the database already trusts. 

Before executing my active mapping, I expect the domain controller to record specific categories of authentication and directory activity resulting from my planned work. When I map Active Directory permissions, the DC will record LDAP bind requests and directory queries. As I request tickets for target services, the DC will log Kerberos authentication events, specifically TGT requests (Event ID 4768) and Service Ticket requests (Event ID 4769). Anticipating these records dictates how I structure my requests to blend in with normal traffic.

When deciding which recoverable material is worth cracking, I will prioritize targets strictly by their strategic value—specifically database administrators, service accounts, or identities with delegation rights. To avoid running out of time, I will apply a strict stopping rule: any hash or ticket that survives two hours of targeted dictionary attacks and rule permutations will be permanently abandoned. 

Recovered plaintext credentials will be used to issue precise LDAP queries, request TGTs, and trace the access control lists governing the database server. If I recover authentication material—such as an NTLM hash or a valid Kerberos ticket—but cannot crack the plaintext password within my time budget, that material remains entirely actionable. I will use Pass-the-Hash (PtH) or Pass-the-Ticket (PtT) techniques to inject them directly into my session, authenticating to the target objective exactly as if I had the plaintext password.

To protect the authentication environment and my time budget, the one thing I will absolutely not do on this engagement is conduct broad, automated password spraying. Spraying blindly across the domain generates massive spikes in failed logon events (Event ID 4625), which actively alarms the authentication architecture, risks locking out legitimate business users, and derails the entire operation.
