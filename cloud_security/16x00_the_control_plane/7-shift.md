# 7 — Review: The Shift

At the start I thought that no route to Copperline's machines meant there was little to reach. I now understand that valid credentials create a different route: signed API requests go to the account's control plane, where the identity's permissions decide which data and configuration the account will return. No connection to a dispatch host is needed.

In this account, `svc-audit-intake` was described as read-only access to operations logs. The attached policy's `IntakeSupport` statement instead grants `s3:Get*` and `s3:List*` on `Resource: "*"`. The account returned the otherwise undocumented migration-scratch bucket and its object keys to this identity; `HeadObject` also returned metadata for both keys. That is a concrete expansion of visibility beyond the documented operations-log purpose. The inline policy also contains policy-version management actions against `CopperlineOpsLogsReadOnly`, a separate high-impact capability that must be tested and accounted for. The object listing and `HeadObject` responses disagree on object sizes, and I have not established the object bodies from those responses alone.

A perimeter-only defense would miss this path. Defenders should monitor CloudTrail for IAM policy-version creation and default-version changes, unusual S3 `ListAllMyBuckets`/`ListBucket`/`GetObject`/`HeadObject` activity, access to buckets outside a principal's stated purpose, and denied calls that show probing. Alerting should key on principal, action, resource, source context, and changes from the principal's normal pattern—not only on traffic to servers. Least-privilege review and credential lifecycle controls belong beside network defenses.
