# Granite Peak Energy — Cloud Assessment Report

## Executive summary

Our review confirmed that a credential exposed in Granite Peak's software repository can reach the production environment and read a file containing real-time regional grid load and switching information. If someone used the same production access to change or stop the service collecting that information, operators could rely on stale or inaccurate readings during balancing, fault response, and restoration. That could delay recovery and increase reliability and safety risks. We found no evidence of a grid-control action, outage, external disclosure, or customer impact.

I ask the board to authorize immediate deactivation of the exposed credential and a temporary hold on automated production releases until a replacement access method is verified. Direct operations, security, and counsel to review access to the restricted data. The assessment account lacked permission to deactivate the credential; an account administrator must apply the fix. The credential in repository history was committed on October 28, after the October 19 logged read, so it is not proven to have caused that earlier event. Our current test did confirm that the repository credential works today. The other findings concern broader key access, reporting permissions, and network or admission settings; they are lower priority. We did not determine how many other records were accessed or whether data was disclosed outside Granite Peak.

## Scope and method actually followed

The review covered the supplied architecture, Terraform, identity exports for build account `210000000001` and platform account `210000000002`, cluster exports, platform repository history, and the fortnightly activity record. It compared documented claims with built-state declarations and traced the account trust, cluster deployment capability, workload identity, object access, and encryption-key relationships into the audit events.

The initial interactive AWS CLI replay failed because command text was entered at the credential prompt. A corrected non-interactive replay succeeded: `get-caller-identity` confirmed the repository credential as IAM user `user/ci-runner`, STS returned the `gp-deploy` and `gp-telemetry-reader` identities, and `s3api get-object` read the named 4,368-byte object to `/dev/null`. Attempts to deactivate the key and update the trust policy were denied by the account API (`AccessDenied` for `iam:UpdateAccessKey` and `iam:UpdateAssumeRolePolicy`), so no live remediation or post-fix denial test is claimed. Network reachability, full effective IAM permissions, and complete admission behavior were not independently tested. The object response had null encryption metadata; `get-bucket-encryption` and `kms:DescribeKey` inspection calls were denied to the reader identity, so encryption configuration is supported by Terraform rather than those API reads.

## Findings

### F-01 — Build identity reached production deployment and telemetry access

**Critical; highest priority.** `infrastructure/identity/gp-deploy.tf` trusts build role `ci-runner`; `identity-export/platform-account.json` shows `gp-deploy-policy` grants `eks:*` and wildcard S3 object actions. `cluster-export/clusterrolebindings.yaml` binds the platform deployer to a role with deployment update and patch rights. `cluster-export/workloads/platform/deployments.yaml` shows `telemetry-ingest` running as `node-agent`. The identity export identifies EC2-trusted `gp-telemetry-reader` as the node instance-profile role, with S3 read access to `gp-grid-telemetry` and KMS decrypt on the shared key.

The activity log at `granite-peak/activity/granite-peak-trail.jsonl` records, with `errorCode: null`, `ci-runner` assuming `gp-deploy` at 2026-10-19 02:00Z; assumed `gp-deploy` updating `telemetry-ingest` in `platform` at 02:03Z; and `gp-telemetry-reader` reading `gp-grid-telemetry/load/2026-grid.ndjson` at 02:12Z. This is the highest consequence because it crosses account, cluster, workload, identity, storage, and key boundaries and ends in a successful read of Granite Peak's most sensitive classified data.

The repository history contains a CI access key in `.ci/deploy.env`, commit `d3ce67de7c82ee8db4b6855347b9c0ef1ccee0b1`, dated 2026-10-28. That is nine days after the activity events; the record does not prove it was used for the October 19 session. No secret values are reproduced. The exact deployment payload, number of objects accessed, and any external disclosure are not established.

In the live replay, that repository credential returned caller ARN `arn:aws:iam::210000000001:user/ci-runner`, while the trust export names `arn:aws:iam::210000000001:role/ci-runner`. The account API nevertheless accepted the subsequent assume-role call to `gp-deploy`. This caller/principal mismatch should be reconciled with the account owner; the successful API response, not an assumed equivalence between the ARNs, proves the tested transition.

### F-02 — Shared platform key does not meet documented narrow custody

**Medium.** `infrastructure/storage/grid-telemetry.tf` selects `alias/gp-platform-shared`; `infrastructure/storage/kms.tf` allows account-root decrypt and data-key generation on `Resource: "*"`; and the identity export grants `gp-telemetry-reader` decrypt. This conflicts with the architecture's tightly held, telemetry-only key claim and contributes to the main chain. The supplied policy does not establish that every platform role can decrypt.

### F-03 — Reporting role has broad read and discovery permissions

**Medium.** `identity-export/platform-account.json` attaches `gp-reporting-broad` (`*:Describe*`, `*:List*`, and `*:Get*` on `*`) to EC2-trusted role `gp-reporting`. The activity file shows ordinary reads by that role. The policy expands information access but contains no write actions in the supplied export and is not connected to the deployment path.

### F-04 — App route contradicts analytics isolation documentation

**Low.** `infrastructure/network/route-analytics.tf` declares a route from `rtb-app` to `10.3.0.0/24` over `pcx-app-analytics`; `vpc-subnet-03.tf` tags that range as analytics. The architecture diagram says there is no route. A configured route is established, but permitted connectivity and a path to telemetry are not.

### F-05 — Admission enforcement differs from the architecture statement

**Low.** The architecture says pod security is enforced in every namespace. `cluster-export/admission/bindings.yaml` binds `pod-security-baseline` with `validationActions: [Audit]`, recording policy violations instead of rejecting them at admission. No violating workload or connection to the telemetry access is evidenced.

### F-06 — App HTTPS ingress uses a broad private source range

**Low.** `infrastructure/network/sg-app-00.tf` through `sg-app-05.tf` permit TCP/443 from `10.0.0.0/8`, not workload-specific source ranges. This is broader than necessary but not internet-wide and is not linked to the telemetry chain.

## Cleared conditions and sound controls

The bucket named `granite-peak-public-grid-data` is not shown to be anonymously readable in the supplied configuration. The complete bucket policy in `infrastructure/storage/public-grid-data.tf` contains one statement: it denies every S3 action to every principal on every resource when the request does not come through `vpce-gp-prod`; it contains no allow. A request through that endpoint still needs a separate allow. I did not verify the live bucket policy or endpoint through the account API.

The `cluster-admin-break-glass` ClusterRole in `cluster-export/clusterroles.yaml` grants only pod `get` and `list`. I checked both binding files: `clusterrolebindings.yaml` binds `platform-deployer`, while `rolebindings.yaml` binds the namespaced `sandbox-admin` Role. Neither binds the alarming ClusterRole, so the export shows no subject receiving its permissions.

The `gp-break-glass` Terraform policy has wildcard actions and resources only when the caller has `break-glass=approved`; the condition is an additional restriction, not the main clearance. `identity-export/platform-account.json` lists attached policies for the exported roles and its policy inventory, and neither contains `gp-break-glass`; the Terraform tree also defines no attachment for it. An unattached policy does not grant its wildcard actions to a principal in this exported snapshot. Live attachment enumeration could not be confirmed because the assessment identity was denied `iam:ListEntitiesForPolicy` and `iam:ListRoles`; this clearance is limited to the supplied snapshot.

The app security groups permit TCP/443 from private `10.0.0.0/8`, not the public internet. This clears an internet-wide exposure claim, while the broader-than-needed private source range remains F-06 at Low. The live state of these controls was not independently queried where noted; the findings describe the supplied configuration and exports.

## Material chain and business impact

The full chain and evidence for each transition are in `3-chain.md`. The repository credential was executed against the account API and identified as `ci-runner`; that identity successfully assumed `gp-deploy`; the cluster configuration and October 19 audit event establish the deployment role's update capability and its successful `telemetry-ingest` update; the workload configuration associates the deployment with `node-agent`; from the `gp-deploy` session, the assessment successfully assumed `gp-telemetry-reader` and read `load/2026-grid.ndjson`. The repository credential commit is later than the October 19 event and is not claimed as that session's credential source.

The demonstrated result is access to one named object classified by the architecture as real-time grid load and switching telemetry. Inference from that documented function: access to current load and switching state could help an attacker identify operating conditions or choose a time and target for disruption. A deployment change that alters or stops `telemetry-ingest` could leave operators with inaccurate or stale telemetry during balancing, fault response, and restoration, delaying diagnosis and recovery and increasing reliability and safety risk. The evidence does not show telemetry was altered, grid equipment was controlled, an outage occurred, or a customer was affected. The chain crosses teams responsible for CI, account trust, cluster deployment, workload identity, and data/key management, so reviewing each team's configuration in isolation would miss how the path composes.

## Remediation programme

1. **Contain F-01 at the credential and trust boundary.** Have an authorized IAM administrator deactivate the repository-exposed key, reconcile why its live caller is IAM user `user/ci-runner` while the exported `gp-deploy` trust names role `ci-runner`, and remove or suspend that production trust until the identity is understood. Hold automated production releases during the change. Replace the long-lived key path with a short-lived identity restricted to the approved repository/workflow, then replace `eks:*` and wildcard S3 rights with only the deployment operations and resources required. Verify that the old key can no longer authenticate and the replacement cannot read telemetry or update an unapproved workload. The assessment identity was denied `iam:UpdateAccessKey` and `iam:UpdateAssumeRolePolicy`; no live fix or post-fix test is claimed. **Cost/dependency:** releases pause while CI and IAM owners coordinate and test a replacement; an overly narrow policy may block a legitimate deployment, so validate it in a controlled release before resuming.
2. **Remove the workload-to-node credential path (F-01/F-02).** Assign `telemetry-ingest` a dedicated workload identity, block its pods from obtaining node credentials, and remove `gp-grid-telemetry` and its KMS decrypt rights from the shared node role `gp-telemetry-reader`. Confirm that the dedicated identity can read only the ingestion objects it needs and that a test pod cannot use node credentials. **Cost/dependency:** cluster and application owners must test the credential change and ingestion flow; a bad rollout can interrupt telemetry collection, so use a staged deployment and rollback plan.
3. **Replace the shared key (F-02).** Move `gp-grid-telemetry` to a telemetry-specific customer-managed key, grant decrypt only to the approved workload identity and designated key administrators, and remove broad account-root effective use where it is not required. Re-encrypt or otherwise preserve access to existing objects, then test key rotation and recovery. **Cost/dependency:** storage and key owners need a migration window and recovery validation; mishandled migration can make historical telemetry unreadable.
4. **Scope the reporting role (F-03).** Inventory the reports and the resources they actually use, replace `gp-reporting-broad` (`*:Describe*`, `*:List*`, `*:Get*` on `*`) with service-specific read actions and named resources, and test scheduled reports before removing the broad policy. **Cost/dependency:** reporting owners must identify real dependencies; reports may fail until their required reads are mapped.
5. **Remove or constrain the app-to-analytics route (F-04).** Confirm whether dashboards or data jobs require the `rtb-app` route to `10.3.0.0/24`; if not, remove it, and if so, narrow it to the required source/destination and ports. **Cost/dependency:** network and analytics owners must test those flows first; removing a relied-upon route may interrupt dashboards or jobs.
6. **Narrow app ingress (F-06).** Replace TCP/443 from `10.0.0.0/8` in `sg-app-00` through `sg-app-05` with the smallest verified caller ranges and ports. **Cost/dependency:** application owners must inventory callers and test health checks and internal clients; missing a legitimate caller can make an app unavailable to that service.
7. **Set and verify admission enforcement (F-05), then close evidence gaps.** Confirm the intended pod-security mode, test representative workloads, and change `validationActions: [Audit]` to the approved blocking mode only after exceptions are resolved. Separately obtain authorized live reads of bucket endpoint policy, key policy, deployed admission state, logging and seven-year retention, then update architecture records to the verified state. **Cost/dependency:** platform owners must validate workloads and governance owners must confirm retention requirements; blocking existing workloads can prevent deployments, and verification depends on read access unavailable to this assessment identity.

If only the first item is completed, it removes the broad build-to-production transition while the remaining work addresses workload credential isolation and key access. The detailed sequence and operating costs are in `4-remediation/4-programme.md`.

## Detection guidance from Granite Peak's records

**Earliest useful signal:** in `granite-peak/activity/granite-peak-trail.jsonl`, at `2026-10-19T02:00:00Z`, build identity `arn:aws:iam::210000000001:role/ci-runner` called `sts.amazonaws.com` / `AssumeRole` with `requestParameters.roleArn` set to platform role `...:role/gp-deploy`; `errorCode` is null. This is the first unusual identity action to alert on: the supplied fortnight shows this as the only `ci-runner` assumption into `gp-deploy`, while surrounding records show routine application reads and instance descriptions. It is the early signal, before the sensitive object read.

**Corroboration and scope:** at `02:03:00Z`, `arn:aws:sts::210000000002:assumed-role/gp-deploy/ci-session` called `eks.amazonaws.com` / `UpdateDeployment`, with `requestParameters.name=telemetry-ingest` and `namespace=platform`, `errorCode=null`. At `02:12:00Z`, `arn:aws:sts::210000000002:assumed-role/gp-telemetry-reader/i-node` called `s3.amazonaws.com` / `GetObject`, with `requestParameters.bucketName=gp-grid-telemetry` and `key=load/2026-grid.ndjson`, `errorCode=null`. Treat the deployment update and later object read as corroboration and impact scoping, not as the first alert. The file also records ordinary nearby activity, including `gp-app-03` listing objects at 02:28Z, `gp-app-17` describing instances at 02:41Z, and `gp-app-00` listing objects at 02:48Z. Correlate timestamp, caller ARN, source, event name, role ARN, deployment name/namespace, bucket/key, and error code; preserve the full events and compare the caller's actions with its historical baseline. The supplied file begins October 10, making the first unusual chain event on October 19 its ninth day; the log window does not prove when the exposure began.

## Data classification and counsel handoff

The architecture document classifies real-time regional grid load and switching telemetry as `operational-restricted` and explicitly places that category in Granite Peak's governed data-handling process: authorized access, adequate protection at rest, access logging, and seven-year retention. It also says Granite Peak's internal process treats a failure of access control or protection as reportable internally, requiring an access review and client notification. These are facts about the supplied architecture and its stated process, not a conclusion about an external legal rule.

The historical activity record shows `gp-telemetry-reader` successfully reading `gp-grid-telemetry/load/2026-grid.ndjson` at `2026-10-19T02:12:00Z`. Separately, the assessment replay later confirmed successful access to that same named object through `gp-deploy` and `gp-telemetry-reader`; the exact replay timestamp was not retained, so it is not used to extend or date the historical exposure. The export covers October 10–23 and does not establish the first exposure date, continuous access, the full set of objects read, or external disclosure. The identity and workload exports identify the reader role and its node/workload relationship; the API replay proves the tested role transition and object read. The facts for counsel are therefore: a named operational-restricted telemetry object was read by the reader role on October 19, and the assessment later reproduced a read through the tested deployment path. Granite Peak counsel should determine the legal significance, applicable notification decisions, and any further duties after establishing the full access scope. This assessment records the evidence and Granite Peak's stated internal response; it does not decide the legal obligation.

## Limitations

The pre-fix identity and object-read path was executed against the local account API. The assessment identity could not deactivate the key or change the trust policy (`iam:UpdateAccessKey` and `iam:UpdateAssumeRolePolicy` were denied), so containment and post-fix denial were not tested; IAM list calls were also denied, so the live `gp-break-glass` attachment state was not verified. The Terraform and identity export support the reported snapshot conclusions, not an assertion about later live changes.

The review did not independently test packet-level connectivity for the app route or security groups because the estate provides no route to the cloud outside its local audit API; it did not query the deployed bucket endpoint policy, deployed key policy/encryption setting, or seven-year retention because the assessment identity lacked those read permissions. The cluster is represented by exported state rather than a live Kubernetes session, so complete admission behavior, actual pod-to-node credential delivery, and the exact October 19 deployment payload were not verified. The fortnight activity export is not a complete audit history, and it does not show all data access, external egress, or whether the October 19 session used the key later committed on October 28. These limits bound what can be concluded; they do not establish that untested controls are safe.
