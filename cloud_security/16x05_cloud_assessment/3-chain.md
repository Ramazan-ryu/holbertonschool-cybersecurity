# Material Exposure Chain

## Evidence standard

This chain combines repository history, Terraform, identity and cluster exports, and the supplied account activity. The workstation transcript's attempted AWS CLI replay failed because the interactive credential prompt was not completed; later commands therefore had incomplete or absent credentials. No failed CLI call is represented as successful proof. The activity log records successful operations by the relevant identities (`errorCode: null`). It provides the caller ARNs and successful actions, but the supplied terminal output does not include a successful `aws sts get-caller-identity` response or a separate permission-test response. Do not treat the CLI replay as independently completed.

## Steps

1. **A CI credential is present in source history; its link to the logged session is not proven.** The supplied `git log -p -S` output shows `.ci/deploy.env` added in commit `d3ce67de7c82ee8db4b6855347b9c0ef1ccee0b1`, dated 2026-10-28, with an AWS access key ID and secret. The activity sequence below is dated 2026-10-19. The commit therefore demonstrates credential exposure in repository history, but cannot be the source of credentials used nine days earlier. The precise credential used in the logged session remains unknown. Secret values are omitted.
2. **Build identity is trusted by the production deployment role, and the trust was used.** `infrastructure/identity/gp-deploy.tf` sets the trusted AWS principal to `arn:aws:iam::210000000001:role/ci-runner`. The platform identity export lists the same trust and attaches `gp-deploy-policy`, which allows `eks:*` and S3 object reads/writes on `*`. The activity record at **2026-10-19 02:00Z** records build-account `ci-runner` invoking STS `AssumeRole` with `roleArn` `...:role/gp-deploy` and no error; at **02:03Z** the assumed `gp-deploy` identity invokes EKS `UpdateDeployment` for `telemetry-ingest` in `platform`, also with no error. This proves the logged identity transition and accepted operations, not that the later-committed repository credential was used.
3. **Deployment identity can change the workload.** `cluster-export/clusterrolebindings.yaml` binds `platform-deployer` to service account `deployer` in `platform`; `cluster-export/clusterroles.yaml` gives it `get`, `list`, `update`, and `patch` on deployments. `cluster-export/workloads/platform/deployments.yaml` identifies the target deployment and its `serviceAccountName: node-agent`. The successful 02:03Z activity event independently confirms an update request for the named workload. It does not preserve the changed pod specification, so the exact payload is not established by the log excerpt.
4. **The workload's node identity can read telemetry, and the object read succeeded.** The identity export states that `gp-telemetry-reader` trusts EC2 and is the node instance-profile role. The deployment uses `node-agent`; at **2026-10-19 02:12Z**, the activity record identifies `gp-telemetry-reader` as the caller of S3 `GetObject` for the telemetry bucket and key below, with no error. This proves the role accessed the named object. The exact mechanism by which a changed pod obtains node credentials was not independently replayed; the workload and node role relationship is supported by the supplied configuration exports and the correlated successful events.
5. **Data and key are identified.** `identity-export/platform-account.json` grants `gp-telemetry-reader` `s3:GetObject` and `s3:ListBucket` on `gp-grid-telemetry`, and KMS decrypt on `gp-platform-shared`. `infrastructure/storage/grid-telemetry.tf` configures the bucket for that shared key; `infrastructure/storage/kms.tf` grants the account root decrypt and data-key generation. The activity event records successful `GetObject` for `gp-grid-telemetry/load/2026-grid.ndjson`. The architecture classifies real-time grid load and switching telemetry as **operational-restricted** and says access is governed with seven-year retention and logging. The object body was not retrieved in the workstation replay, so content is identified from the client classification and object path, not independently inspected.

## Why this is a cross-domain chain

The repository history, build-account identity, platform trust policy, cluster RBAC, workload service-account configuration, EC2 node identity, S3 data policy, and KMS policy are owned and represented in different artefact sets. Reviewing any one domain in isolation can make its component look ordinary: a CI role, a deployment role, a node role, and a telemetry bucket. Their composition crosses account, cluster, workload, and storage boundaries and is what makes the exposure material.

## Business consequence and bounds

The demonstrated record is a successful read of one named 2026 grid telemetry object by `gp-telemetry-reader`, following a recorded CI-to-deployment event. The access chain is evidenced by successful audit events and configurations; the credential source for the October 19 CI session is not identified, and the repository credential commit is later. This establishes access to the named object, not the total number of objects read, external exfiltration, modification of grid controls, or an operational outage. A party able to control the telemetry ingestion workload could also affect the integrity or availability of that service; the provided activity entry does not show what deployment payload was used or that grid switching operations were changed. Granite Peak should treat confidentiality of this classified operational data as exposed and have platform, operations, and counsel determine the broader incident scope.
