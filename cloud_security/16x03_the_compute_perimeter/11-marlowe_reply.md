# 11 — Reply to Marlowe Commerce

Dear Marlowe team,

The catalog image-import feature accepts a caller-selected URL. A request for `http://example.com/` returned the remote page, while the preview and redirect controls rejected the tested metadata URL. The same image-import path fetched the instance-role metadata credentials. STS identified the resulting principal as `arn:aws:sts::500100200300:assumed-role/marlowe-web-instance-role/i-0marlowe`. Calls made with that session succeeded for S3 `GetObject` on `orders/2026-Q1.json`, SQS `ReceiveMessage` on `marlowe-customer-events`, and Secrets Manager `GetSecretValue` on `marlowe/stripe-webhook-signing`; `iam:ListUsers` was denied. Secret and message contents are omitted.

The instance-role session later assumed `marlowe-order-processor-role` as `perimeter-review`. The confirmed function-role session enumerated two S3 buckets, one secret name, one queue, and four IAM users; it also received a successful empty DynamoDB table listing. These are the specific accepted inventory calls recorded in the lab export. The handler source independently contains seven required operations. The execution role policy has not been narrowed: `iam:CreatePolicyVersion` was denied, so the proposed resource-scoped policy remains unapplied and lacks post-change security and functionality tests. An account administrator must apply it, then verify that the same previously successful excess call is refused and a required call succeeds under a fresh role session.

We recommend retaining strong IMDS mode first. Replaying the same tokenless metadata request under strong mode returned HTTP 502 without credential fields; the earlier weak-mode request returned credential data. This interrupts the tested metadata credential path. It does not fix the application SSRF: image-import still accepts attacker-controlled destinations. The application should enforce a strict destination allowlist, validate scheme, hostname, and resolved IP addresses, revalidate redirect destinations, and restrict outbound egress. Role narrowing remains a separate necessary control.

The network review found the ACL's request/reply asymmetry: its inbound TCP/8080 rule does not authorize a reply to an ephemeral client port, and its outbound TCP/443 rule only names `10.0.1.0/24`. The public security-group egress rule therefore does not establish public reachability. The app-to-analytics peering path is blocked by non-transitive peering. The S3 endpoint policy is permissive, but subnet associations, endpoint routes, and return-flow ACL permission are absent, so end-to-end host-to-endpoint reachability is unknown. The handover's S3 question cannot be resolved beyond those control-level facts.

The dependency package pins boto3 1.34.69, PyYAML 5.3.1, and requests 2.31.0. Trivy reported candidates for PyYAML and requests, but the supplied handler uses boto3 and JSON and does not show those dependencies' affected code paths. The scanner ratings alone do not establish exploitability. Lambda configuration retrieval returned `SignatureDoesNotMatch`; therefore any configuration-held credential and the deployed execution-role attachment remain unverified.

For detection, prioritize an owner-approved baseline for STS `AssumeRole` into `marlowe-order-processor-role`. Record caller, target role, session name, time, source address, and available runtime/network context; compare them to expected principals and origins, then correlate the resulting `GetCallerIdentity` session with later API calls. The observed instance-role-to-function-role transition is a candidate cross-workload context anomaly, not proof of unauthorized use. The export is lab-generated, its HMAC is not independently verifiable here, and `127.0.0.1` appears on both workload and reviewer/operator calls; it does not establish an impossible physical origin. Owner confirmation is needed for the intended trust and deployment boundary. Approved testing, deployment tooling, break-glass use, proxies, failover, and architecture or egress changes can produce legitimate baseline mismatches. Maintaining the baseline and investigating alerts will cost engineering and analyst time; no false-positive rate has been measured.
