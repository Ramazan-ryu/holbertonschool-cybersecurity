# 1. Who Said No

This is the authorization-refusal inventory. Each request was made with the stated principal and resource. The governing statements below provide the attribution; the generic `AccessDenied` response alone does not.

## Refusals and governing statements

1. **KMS Decrypt — identity explicit deny.** Principal: `arn:aws:iam::418274630117:user/reporting-analyst`. Call: `aws kms decrypt --ciphertext-blob fileb:///dev/null --key-id alias/ashford-reporting`. Response: `AccessDeniedException`, `not authorized to perform: kms:Decrypt`; CloudTrail `Decrypt` at `2026-11-19T03:26:46Z` and `03:44:48Z`. `ReportingAnalystAccess`, `Sid: NoDecrypt`, is `Effect:Deny`, `Action:"kms:Decrypt"`, `Resource:"*"`. This explicit identity-policy deny removes Decrypt.

2. **CreateAccessKey — SCP explicit deny overrides identity allow.** Principal: same user; target user: `reporting-analyst` in account `418274630117`. Call: `aws iam create-access-key --user-name reporting-analyst`. Response: `AccessDenied`; CloudTrail `CreateAccessKey` at `03:27:32Z` and `03:44:49Z`. The identity statement `SelfKeyManagement` is `Effect:Allow`, `Action:["iam:CreateAccessKey","iam:ListAccessKeys"]`, `Resource:"arn:aws:iam::418274630117:user/reporting-analyst"`. The attached boundary `CapRead` also includes `iam:*` on `*`, so neither removes this action. The organization SCP `AshfordGuardrails`, `Sid: NoLongLivedKeys`, is `Effect:Deny`, `Action:["iam:CreateAccessKey","iam:CreateLoginProfile"]`, `Resource:"*"`. That SCP deny controls the result.

3. **S3 PutObject — permissions-boundary cap.** Principal: same user; bucket/key: `ashford-reporting-ap7f3a/evidence/probe.txt`. Call: `aws s3api put-object --bucket ashford-reporting-ap7f3a --key evidence/probe.txt --body /tmp/ashford-probe.txt`. Response: `AccessDenied`; CloudTrail `PutObject` at `2026-11-19T05:31:31Z`. Identity statement `ReportingReadWrite` is `Effect:Allow`, `Action:"s3:*"`, `Resource:["arn:aws:s3:::ashford-reporting-ap7f3a","arn:aws:s3:::ashford-reporting-ap7f3a/*"]`. Boundary `ReportingAnalystBoundary`, `Sid: CapRead`, is `Effect:Allow`, actions including `s3:Get*` and `s3:List*`, `Resource:"*"`; it has no `s3:PutObject` grant. A boundary is an intersection cap, not an independent grant, so the identity allow does not authorize PutObject.

4. **SQS ReceiveMessage in wrong region — condition not satisfied.** Principal: same user; queue URL: `http://127.0.0.1:4566/418274630117/ashford-dispatch-events`. Call: `aws --region us-east-1 sqs receive-message --queue-url ... --max-number-of-messages 1`. Response: `AccessDeniedException`; CloudTrail `ReceiveMessage` at `03:26:14Z` and `03:28:40Z`. Statement `DispatchQueueHomeRegionOnly` is `Effect:Allow`, actions `["sqs:GetQueueAttributes","sqs:GetQueueUrl","sqs:ReceiveMessage"]`, `Resource:"*"`, condition `StringEquals:{"aws:RequestedRegion":"eu-west-1"}`. The request context was `us-east-1`; thus the statement did not match and no other identity allow applied. This is an implicit identity-policy deny. The same queue operation in `eu-west-1` succeeded.

5. **AssumeRole into dev — caller identity-policy scope.** Principal: same user; requested resource: `arn:aws:iam::418274630228:role/ashford-dev-maintenance`. Call: `aws sts assume-role --role-arn arn:aws:iam::418274630228:role/ashford-dev-maintenance --role-session-name boundary-review`. Response: `AccessDenied`, naming the reporting user; CloudTrail `AssumeRole` at `2026-11-19T05:29:41Z`. The only relevant identity allow, `ChainB_AssumeReader`, is `Effect:Allow`, `Action:"sts:AssumeRole"`, `Resource:"arn:aws:iam::418274630117:role/ashford-crossacct-reader"`; no condition broadens that resource. The dev trust is `Effect:Allow`, `Principal:{"AWS":"arn:aws:iam::418274630117:root"}`, `Action:"sts:AssumeRole"`, so the receiving trust agrees with the prod account. The refusal is the caller's missing identity grant, not the trust, boundary, or SCP. The later successful call used a different principal: the assumed admin role.

6. **CreateUser in the original CLI session — implicit identity-policy deny.** Principal at request time: `arn:aws:iam::418274630117:user/reporting-analyst`, as shown in both the `CreateUser` error and `aws sts get-caller-identity`; requested resource: user `proof`. Call: `aws iam create-user --user-name proof`, after `assume-role` had printed credentials but before they were installed into the CLI session. Response: `AccessDenied`, explicitly naming `user/reporting-analyst`; CloudTrail `CreateUser` at `03:45:29Z`. The reporting identity policy has no `iam:CreateUser` allow; its `SelfKeyManagement` statement covers only CreateAccessKey and ListAccessKeys on the analyst user. This is not a refusal of the assumed role: the command remained signed as the original user.

7. **Lambda Invoke — identity action does not match the endpoint's evaluated action.** Principal: same user; function: `ashford-boundary-probe`. Call: `aws lambda invoke --function-name ashford-boundary-probe --payload '{}' --cli-binary-format raw-in-base64-out /tmp/ashford-invoke.json --region eu-west-1`. Response: HTTP 403 `AccessDenied`, naming `lambda:Invoke`; CloudTrail event ID `856cae85-1921-44d5-98e2-7954aa145d8a` at `2026-11-19T06:15:12Z`. In the configured identity policy, `ChainA_Compute` allows `lambda:InvokeFunction`, not the action string `lambda:Invoke` returned by this endpoint; there is no matching identity allow for the action it evaluated. The boundary's `lambda:*` is only a cap and does not grant it. This is an implicit identity-policy deny for the request as the endpoint evaluated it, and it prevents claiming that the function ran under the batch role.

8. **CreateFunction after remediation — missing required PassRole grant.** Principal: `arn:aws:iam::418274630117:user/reporting-analyst`; requested execution role: `arn:aws:iam::418274630117:role/ashford-batch-exec`. Call: `aws lambda create-function --function-name ashford-boundary-after-fix --runtime python3.12 --role arn:aws:iam::418274630117:role/ashford-batch-exec --handler handler.handler --zip-file fileb:///tmp/probe.zip`. Response: HTTP 403 `AccessDenied`, naming `lambda:CreateFunction`; CloudTrail event ID `3e317ddd-b30d-452c-aae7-497672061f69`, request ID `XpxjjFFTmP7KtjodsutsgVv9uPeGvbVIQUDIOgjOGpc5BUj9raXu`, at `2026-11-19T06:41:25Z`. `ReportingAnalystAccess` v2 retains `ChainA_Compute` (`Effect:Allow`, `Action:["lambda:CreateFunction","lambda:InvokeFunction","lambda:DeleteFunction"]`, `Resource:"*"`) but the remediation removed the only `iam:PassRole` allow on the requested role. The call requires that service-role handoff as well as Lambda creation; the request is refused because the identity policy no longer supplies the handoff permission. The boundary contains `iam:*` and `lambda:*`; it cannot re-grant the removed identity permission. This is an identity-policy missing-allow result, demonstrated on the same principal and resource after the policy change.

## What the pattern says about Ashford

The controls target distinct risks: explicit denial of KMS decryption limits exposure of reporting data; the SCP blocks creation of long-lived credentials across accounts; the boundary keeps Finance's S3 grant read-only; and the SQS condition confines queue access to the home region. The dev trust allows the prod account but the user's identity grant remains scoped to one role. This is evidence of intentional governance around data confidentiality, durable credentials, regional operations, and cross-account access. Those controls are effective within their scopes, but they do not prevent the separately documented policy-version or service-role compositions.
