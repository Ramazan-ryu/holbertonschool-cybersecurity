# 1. Who Said No

The refusals below were made by different authorization layers. AWS often returns the same generic `AccessDenied`; the governing statement identifies the layer.

| Call and response | Layer and governing statement | Why |
|---|---|---|
| `aws kms decrypt --ciphertext-blob fileb:///dev/null --key-id alias/ashford-reporting` → `AccessDeniedException` for `kms:Decrypt` (CloudTrail `Decrypt`, `2026-11-19T03:26:46Z`, later `03:44:48Z`). | Identity policy `ReportingAnalystAccess`, `Sid: NoDecrypt`, `Effect: Deny`, `Action: kms:Decrypt`, `Resource: *`. | An explicit identity-policy deny wins over any allow. |
| `aws iam create-access-key --user-name reporting-analyst` → `AccessDenied` (CloudTrail `CreateAccessKey`, `03:27:32Z`, `03:44:49Z`). | SCP `AshfordGuardrails`, `Sid: NoLongLivedKeys`, explicitly denies `iam:CreateAccessKey` and `iam:CreateLoginProfile` on `*`. | The identity policy's `SelfKeyManagement` statement allows `CreateAccessKey`, but the organization SCP caps the account and explicitly denies the request. |
| `aws s3api put-object --bucket ashford-reporting-ap7f3a --key evidence/probe.txt --body /tmp/ashford-probe.txt` → `AccessDenied` (CloudTrail `PutObject`, `05:31:31Z`). | Permissions boundary `ReportingAnalystBoundary`, `Sid: CapRead`. It allows S3 `Get*`/`List*` but not `s3:PutObject`. | `ReportingAnalystAccess` grants `s3:*` on the reporting bucket, but a permissions boundary only caps identity permissions and grants nothing. |
| `aws --region us-east-1 sqs receive-message --queue-url http://127.0.0.1:4566/418274630117/ashford-dispatch-events` → `AccessDeniedException` (CloudTrail `ReceiveMessage`, `03:26:14Z`, `03:28:40Z`). | Identity policy `ReportingAnalystAccess`, `Sid: DispatchQueueHomeRegionOnly`, has a conditional allow only when `aws:RequestedRegion` is `eu-west-1`. | At `us-east-1` the allow statement does not match, leaving no applicable allow. This is an implicit identity-policy deny. At the configured `eu-west-1`, the same operation returned a message. |
| `aws sts assume-role --role-arn arn:aws:iam::418274630228:role/ashford-dev-maintenance --role-session-name boundary-review` → `AccessDenied` (CloudTrail `AssumeRole`, `05:29:41Z`). | Calling identity policy `ReportingAnalystAccess`, `Sid: ChainB_AssumeReader`, grants `sts:AssumeRole` only on `arn:aws:iam::418274630117:role/ashford-crossacct-reader`. | The user is not authorized to request the dev role. The target dev trust does trust the prod account root; later the assumed admin role successfully crossed into dev. The refusal was from the caller's identity policy, not the receiving trust or SCP. |
| Supplied CLI call `aws iam create-user --user-name proof` after `assume-role` printed credentials → `AccessDenied`, naming `user/reporting-analyst` (CloudTrail `CreateUser`, `03:45:29Z`). | No denial from the assumed role: the request was signed by the original identity. | `get-caller-identity` was still the user. Using the STS credentials in a boto3 session returned the assumed-role ARN and successfully created/deleted a temporary user. |

The malformed `s3api put-object --body f` and initial Lambda `--zip-file fileb://f.zip` attempts failed local CLI parameter/file validation, so AWS made no authorization decision. Lambda `Invoke` and `DeleteFunction` returned `SignatureDoesNotMatch`; those are endpoint signing failures, not IAM denials. After remediation, Lambda `CreateFunction` returned `AccessDenied` when the required PassRole edge had been removed; that result is documented in `6-remediation/README.md`.

Ashford has deliberately prioritized three concerns: no long-lived keys (after the 2024 review), no decrypt of reporting data, and read-only/reporting access capped by a boundary. Region locking also narrows queue access. The controls are real, but they leave unrelated privilege-composition paths open; the current permission design blocks isolated actions while allowing policy mutation and service-role handoff to combine into admin access.
