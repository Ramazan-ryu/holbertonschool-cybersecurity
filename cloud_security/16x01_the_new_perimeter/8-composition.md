# 8. Review: Nothing Was Broken

`reporting-analyst` was explicitly allowed to create a policy version for `AshfordCrossAcctReaderAccess` and explicitly allowed to assume `ashford-crossacct-reader`. The role's trust explicitly named that user. I used the first permission to make a default policy version granting `Action:"*"` on `Resource:"*"`; I used the second to assume the now-admin role. A boto3 session built from the returned STS credentials reported the assumed-role identity and successfully created and deleted a temporary IAM user. Each API behaved as configured. Administrative control came from composing policy mutation with a trusted role transition.

The monthly clean scan was evidence that its checks did not flag the component permissions; it was not evidence that the graph of reachable permissions was safe. A scanner that reports individual policy findings can correctly rate a scoped policy-version permission and a scoped role assumption as ordinary, while missing their combined effect. Ashford needs attack-path analysis that connects principals to policy mutation rights, tracks which managed policies are attached to assumable roles, evaluates trust policies, and calculates the effective permissions after a version change. It should also detect broad default policy versions and validate OIDC subject constraints. This is a repeatable identity graph and policy-composition review that can run continuously or before policy changes, rather than an unspecified manual review.
