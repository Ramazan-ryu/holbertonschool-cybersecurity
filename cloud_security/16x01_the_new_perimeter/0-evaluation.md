## Prediction divergence

For the fresh replay, the document-derived prediction for the Lambda invoke request was **DENY** because the action evaluated by this estate is `lambda:Invoke`, while the user policy grants the distinct `lambda:InvokeFunction`. My earlier reading treated those strings as interchangeable and therefore predicted Allow. The policy itself is not inconsistent; the exact action name matters. The fresh request's 403 response confirms the corrected prediction. The first malformed S3 probe also did not test IAM: the CLI rejected a nonexistent local body path before sending a request, so it has no allow/deny result to reconcile.
