The CI runner was given permission to create Pods in `platform` so a deployment or debugging workflow could start work there. That is a practical permission, and it may have been operating as intended. The consequence comes from the identity the Pod can select: `platform-deployer` also lets `build/ci-runner` read ServiceAccounts, so the Pod can name `controller-admin` as its ServiceAccount. The existing `platform-controller` Deployment uses that same account, and `platform-controller-admin` binds it to the `cluster-superuser` ClusterRole. A new Pod's token is mounted by default unless its spec disables it. The route is therefore: create platform Pod → select `controller-admin` → receive its mounted token → use the wildcard cluster grant.

The narrow change is to remove only Pod `create` from Role `platform-deployer`, keeping the read verbs and the ConfigMap/ServiceAccount reads. That stops this specific “launch a Pod as the controller” path at its first step. It also means the CI workflow can no longer launch platform debug Pods; we need to move that workflow to an approved constrained identity or a reviewed operator process before rollout. The audit shows this permission was actually used for `debug-shell-x7k2` (audit log line 826), so the operational dependency deserves a direct conversation rather than an assumption. Nothing about this says the engineer intended cluster-wide access; the hidden link is what `controller-admin` is already allowed to do.
