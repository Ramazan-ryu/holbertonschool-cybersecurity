REQUEST STRUCTURE

The request is not one prompt string. It is a JSON object whose fields are set separately. The conversational content lives in `contents`, an array of turn objects. Each turn carries its own `role` and a list of `parts`, so every message is attributed to a role before it reaches the model.

Roles, one per line, with whether my client sets them:

user — SET BY MY CLIENT. It is the role on the single entry in `contents`. My client chooses both the role and its text ("Say hello in five words."). The proxy's request_structure entry (role user, 24 characters) matches that text length, which is consistent with what I sent.

model — NOT SET BY MY CLIENT in this request, and not present in the request. The reply "Hello, it is nice meeting." is output returned in `text`. It is generated content, not a request turn. If I later replay earlier turns in `contents` with role model, my client would be setting that role, and I would need to say so then.

system — NOT PRESENT, NOT SET BY MY CLIENT. The body has no system instruction field. I cannot see from the client side whether the proxy adds instructions of its own. The response reports only one request entry (role user), so I have no evidence of any proxy-added role, and I make no claim about control over any hidden platform instructions.

CLIENT-SET FIELDS (other than roles)
- student_id: "student"
- mode: "probe"
- temperature: 0.7 (echoed back in the response)
- max_output_tokens: 200
- contents: the single user turn above
