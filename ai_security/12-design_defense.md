# Task 12 — Design Defense

The design uses controls at different points because the model is an unreliable decision maker and no single layer can safely absorb every failure. The controls reduce different classes of harm; each also has a boundary that should be explicit in a review.

**Owned system prompt — instruction-data confusion and prompt injection.** The prompt defines the support role, limits discussion to the signed-in customer's Larkspur account and support topics, prohibits disclosure of other customers' data and staff-only notes, and treats retrieved tickets/articles as reference rather than instructions. This addresses instruction-following failures, prompt extraction, and confusion between trusted instructions and quoted content. Its limit is fundamental: the prompt is model-visible text. A request can induce paraphrase or extraction, and a model update can change how instructions are followed. It cannot enforce account authorization or make a secret safe to place in context. Extraction was not measured successfully here: the attempts returned `upstream_error_502`.

**Parameterized tool output — executable-output injection (SQL injection).** This addresses injection through model-generated database syntax. The database receives a registered statement and named values, so a value containing quote marks or SQL operators remains data. The signed proof showed raw SQL was not executed and an injected value was bound with no canary returned. It does not restrict the set of registered statements, ensure each statement exposes minimal data, or stop a valid but unauthorized request. That is why statement design and per-tool authorization remain necessary.

**Per-tool authorization — broken authorization and cross-account access.** This addresses excessive agency and cross-account access. Each tool independently checks whether the current session can act on the requested target. Four proof calls were denied by `tool:per_tool_authz`; the denial occurred before execution. It does not establish that all future tools have equivalent checks, that identity binding is correct, or that an allowed action is prudent. Tests used plan mode, so live mutation behavior was not exercised.

**Human approval — excessive agency and unsafe consequential actions.** Refund and delete operations pause for a person. The test left the refund pending, queued, and without state change; both listed consequential tools were gated. This addresses irreversible or financially consequential actions that should not be entrusted to model intent alone. The approval gate does not cover unlisted tools or indirect side effects, and a human can approve a harmful request if the screen omits context or the reviewer is deceived. Approval is a pause and decision point, not proof that the decision is sound.

**Retrieval provenance and ingestion restriction — untrusted retrieval and persistent data poisoning.** These address persistent poisoning and untrusted content treated as fact. Public user ingestion is disabled and the planted ticket was quarantined. However, the FAQ-suggestion copy reached retrieval, and `segment_internal=false` means internal content is not separately segmented by the configured retrieval control. The self-attack reached restricted chunks in all three tested embedding searches, and the replay against the supplied external endpoint reported the same 3/3 result. The endpoint owner and build revision are unverified, so this corroborates the technical weakness but is not attributed to a confirmed peer. The victim result was inferred from retrieval rather than tested live, so disclosure remains unproven. Provenance labels can also be laundered if a trusted-looking source republishes untrusted text; the system needs source lineage and review at each transition, not trust based only on the latest container.

**Resource caps — unbounded consumption and runaway tool use.** Session tokens, requests per minute, tool iterations, and output tokens bound runaway generation, tool loops, and cost. The proof terminated the loop at six iterations and hit the 8000-token session cap at call seven under the harness's 1500-token assumption. The actual average-token metric was not supplied, so the cap still needs calibration against normal usage. Caps can also terminate legitimate long requests; they limit impact, not intent.

**Input guardrail and output filtering — adversarial-input evasion, unsafe output handling, and secret exposure.** The input filter scope is only `message`; it does not screen ticket or retrieved channels. It catches some normalized or decodable prompt-injection phrases. The measured bypass was 47/60, including every tested semantic-paraphrase, indirect, multilingual, fake-delimiter, and benign-lookalike variant. It is the weakest control because pattern matching has a narrow view of meaning. Output redaction and schema validation can reduce accidental secret exposure and malformed results, but they cannot prevent data from being fetched or a tool action from occurring. Their rules need direct tests for both leakage and valid support traffic.

**Removal order by vulnerability class under performance or cost pressure:** First dispensable is the phrase-based input filter, which addresses adversarial-input evasion and instruction-data confusion by screening known patterns at message ingress. The 47/60 bypasses show that semantic and indirect variants still pass; removing this layer would increase inputs reaching the agent, so authorization and retrieval controls remain essential. Second is secrecy wording in the system prompt, which addresses prompt injection only through model guidance; model-visible text is not access control, so authorization and output filtering must protect confidentiality. Preserve parameterized statements against executable-output injection, per-tool authorization against broken authorization, approval against excessive agency, provenance and ingestion review against untrusted retrieval and poisoning, and resource caps against unbounded consumption. These enforce separate boundaries. Retrieval remains a material residual: self-testing and the external replay reached internal chunks, though customer disclosure was not demonstrated. Improve segmentation and preserve source lineage through ingestion.
